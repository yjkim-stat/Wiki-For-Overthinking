01The shape of collection

Collection is deterministic Python and calls no model. It fetches, normalizes, scores against the tracked topics, deduplicates, and files a task for anything that still needs reading. The reading itself happens elsewhere, against a file-backed queue. That split is why a slow or failed reading step never costs a day of collection.

Four kinds of source feed it, and they answer different questions:

KindSourcesAnswers
Search arXiv API, Semantic Scholar, DBLP “What matches these keywords?” — a query goes out, a filtered set comes back.
Browse arXiv listing pages, conference programme pages, YouTube channel feeds “What is there?” — the whole set comes back and filtering happens locally.
Follow curated weekly lists “What did somebody outside the group decide mattered?” — a handful of pointers, chosen by judgement rather than by query.
Hand inbox/ “What did someone in the group decide mattered?” — no network at all.

The distinction is load-bearing. A search source can be asked a narrow question and answers cheaply, but it can only return what its index already knows and what its query language can express. A browse source returns everything, which costs more bandwidth but makes a completeness check possible — and the count it reports is the only number in this pipeline that the pipeline did not compute itself.

The two judgement sources are not interchangeable either, and the difference decides whether scoring applies. A PDF in inbox/ bypasses scoring because filing it is the group's editorial decision. A curated list is somebody else's decision, taken over a whole field rather than over the group's topics, so its picks are scored like anything else — being followed is not the same as being wanted.

02The shared HTTP layer

pipelines/common/http.py

Every collector goes through one small client. Nothing reimplements retries or rate limiting, so politeness is a property of the system rather than of whichever collector was written most carefully.

Request defaults

BehaviourSettingDefault
User-Agentcollect.user_agentrecipe-for-research-team-management/0.1 (research archiving bot)
Timeoutcollect.request_timeout_s30 s
Attempts per requestcollect.retries3
Backoffcollect.retry_backoff_s2 s, doubling (2 s, 4 s, 8 s…)
Per-host minimum intervalper collector0–5 s (see each source)
Give up on a host aftercollect.give_up_after_failures5 consecutive whole-request failures

A real User-Agent is not decoration: arXiv and DBLP throttle anonymous clients hard. The interval is enforced per host and shared across collectors, so two collectors touching the same host cannot each spend the full budget.

What counts as retryable

Connection errors, timeouts, OSError, and the whole http.client.HTTPException family — the last of which includes IncompleteRead, raised when a chunked response ends early. That one descends from HTTPException rather than OSError, so it used to escape the retry loop entirely and cost a topic its results mid-run.

A 4xx other than 408 or 429 fails immediately and is not retried: it will not fix itself. A 429 or 408 is retried like a transient error.

The circuit breaker

Retries are scoped to one request, but a run makes hundreds. When a host is down for the whole run, per-request retry turns one dead source into the run's dominant cost and still returns nothing. So the client counts consecutive whole-request failures per host, and after the threshold raises HostUnavailable without attempting a connection.

Design note

HostUnavailable subclasses HTTPError. Every collector already treats that as “this source gave me nothing”, so giving up needed no changes anywhere — and a collector written later inherits the behaviour for free.

A hard 4xx counts toward the breaker deliberately. A 403 to every venue lookup will not resolve inside a run, which makes it a stronger signal than a timeout, not a weaker one. A success resets the counter, so a host that merely blips never trips.

arXiv — the API

pipelines/collect/arxiv.py

GET https://export.arxiv.org/api/query
    ?search_query=(cat:cs.LG OR cat:stat.ML) AND ("causal inference" OR "instrumental variable")
                   AND submittedDate:[202608060000 TO 202608102359]
    &start=0
    &max_results=60
    &sortBy=submittedDate
    &sortOrder=descending

One request per topic, split into several when a topic has many keywords — arXiv rejects very long query strings, so keywords.any is chunked eight terms at a time. Each keywords.all term is ANDed onto every chunk, and multi-word terms are quoted so arXiv treats them as phrases.

The date filter is on submission, not revision. A v2 of an older paper does not resurface here — deliberately, because the archive tracks new work, and revisions of papers it already holds are picked up by the merge in deduplication when they appear through another source.

Authoritative on arXiv identity, abstracts, categories, submission dates. Cannot tell you whether a paper cleared review anywhere.

arXiv — the listing pages

pipelines/collect/arxiv_listing.py

GET https://arxiv.org/list/cs.CL/recent?skip=0&show=250

A second way in, for when the API will not answer. The API and the website are different hosts, and a network policy, a corporate proxy or a rate limit can block one while leaving the other readable.

listing.modeBehaviour
auto (default)Used only when the API returned nothing.
alwaysUsed instead of the API.
neverOff.
Recall cost

The listing carries titles, authors and subjects — no abstracts. So it can only score titles, and a paper whose keywords appear only in its abstract is invisible to it, where the API's all: search would have found it. That is a real loss of recall, and it is why auto is the default: use it when the alternative is nothing at all, not instead of a working API.

Parsing keys on the definition list: a <dt> carrying the /abs/ identifier paired with a <dd> carrying list-title, list-authors and list-subjects. The browse-context sidebar links to /abs/ as well, so matching bare links would invent papers — entries must be a <dt>/<dd> pair. HTML comments are stripped before any structural match, because a comment can contain markup identical to the structure being searched for.

Abstracts for matched titles come from one more request each:

GET https://arxiv.org/abs/2501.00001
→ <meta name="citation_abstract" content="…">
→ fallback: <blockquote class="abstract">…</blockquote>

Semantic Scholar

pipelines/collect/conferences.py

GET https://api.semanticscholar.org/graph/v1/paper/search/bulk
    ?query=("causal inference" | "instrumental variable")
    &fields=paperId,title,abstract,venue,year,authors,externalIds,url,publicationDate,openAccessPdf
    &year=2025-
    &limit=60
    [&venue=NeurIPS,ICLR,ICML]        ← only when restrict_to_venues is true
Header: x-api-key: $SEMANTIC_SCHOLAR_API_KEY   ← optional

The broadest of the conference indexes. Its query language uses | for alternation and + for a required term, so keywords.all becomes (a | b) + c.

Why the venue filter is off by default

Semantic Scholar records a preprint's venue as arXiv.org. Filtering by a list of conference names therefore excludes every preprint, unconditionally — and the result looks like a complete answer: source alive, logs clean, no errors. For a topic whose literature is mostly preprints, that is the whole literature gone.

Off is the right default because the failure mode of false is noise, which scoring already discards, while the failure mode of true is silent absence, which nothing detects. Set restrict_to_venues: true only if the group genuinely reads proceedings versions only.

OpenReview

pipelines/collect/conferences.py

GET https://api2.openreview.net/notes
    ?content.venueid=ICLR.cc/2026/Conference
    &limit=60
    &offset=0

The review-bearing venues, often months before proceedings. Venue ids drift between cycles, so each venue is tried under both the current year and the backfill window's year — a single miss is expected and logged at debug level. Only when every lookup fails is it reported as a source error.

The API wraps every field as {"value": …} in api2 where api1 did not, so the reader tolerates both shapes.

Authoritative on acceptance and review status. Often unavailable answers 403 from many hosts.

DBLP

pipelines/collect/conferences.py

GET https://dblp.org/search/publ/api
    ?q=causal inference venue:ICLR: year:2025:
    &format=json
    &h=60

The bibliographic fallback when the two above miss a venue. DBLP matches on title words only and has no abstract field, so records from here arrive abstract-less and are queried one venue and one term at a time — at most four terms per venue, to keep a run bounded.

ACL Anthology

pipelines/collect/anthology.py

GET https://aclanthology.org/events/naacl-2024/

The proceedings index for the *ACL venues, and the only source here that returns titles, authors and abstracts in a single request. One venue-year is one page, so a paper is scored on the same evidence a reader would have and nothing needs fetching afterwards — the opposite of the arXiv listing, which can score only a title and then spends a request per match on the abstract it lacks.

Two properties of the markup matter. Attributes are served unquoted (href=/2024.acl-long.1/), and letters whose case must survive are wrapped mid-word in acl-fixed-case spans — so InsCL: arrives as three elements, and stripping tags to spaces would turn it into I ns CL :.

An event is not only its conference: the page lists the main tracks, Findings and every co-located workshop, and NAACL 2024 carries roughly eight hundred workshop papers against 958 of the venue's own. A workshop paper is published at the workshop, so the default keeps the venue's tracks and Findings and names in the log what it left out. A venue takes part by carrying an anthology_key; the identifier yields the DOI directly, as 10.18653/v1/<id>.

Conference programme pages

pipelines/collect/virtual_site.py

GET https://icml.cc/virtual/2026/papers.html
GET https://neurips.cc/virtual/2025/loc/san-diego/papers.html   ← split-location years

The venue's own answer to “what did we accept”, available the day the programme goes up rather than when an index gets round to it. The page renders through JavaScript but carries the complete list as plain HTML inside its <noscript> block — a no-JavaScript fallback, and therefore the most stable region of the page.

Only the fallback block is parsed

This is correctness, not tidiness. The navigation bar's login link points at a /virtual/<year>/poster/<id> path too, so a parser sweeping the whole document for that shape would mint a paper titled “Login” from every venue on every run — and it would look like an ordinary record.

Records are minted with a title-fingerprint id, and that is the point of the collector rather than an implementation detail. Most of these papers appeared as preprints first, so the fingerprint makes deduplication merge the listing onto a record the archive already holds. The value is not that the archive gains papers; it is that existing papers learn where they were accepted. Expect data/papers/ records to change without new papers appearing — that is the merge working.

Venues are not on the same cycle: in the second half of a year ICML's current programme is that year's while NeurIPS's is still the previous one, so each venue can pin its own virtual_years.

Curated weekly lists

pipelines/collect/curated.py

GET <curated.lists[].url>                 # an index of issues, or one page
GET <each .md the index links to>          # only for the newest issues
GET https://export.arxiv.org/api/query?id_list=…   # the bibliography

The only source whose selection is a person's judgement rather than a query. An editor reads a field's whole weekly output and publishes ten papers; that is a filter no keyword can reproduce, applied before any keyword sees the paper. The shipped list is DAIR.AI's, whose LinkedIn and Substack editions carry the same papers behind a login wall — the markdown mirror is the fetchable one.

Pointers only, never metadata

A list entry names a paper the way people say it out loud: an acronym, then a paragraph of what the editor found interesting. NOOA is not a title and the commentary is not an abstract, so nothing in the entry becomes a record. Only the linked arXiv id is taken, and the bibliography is fetched from arXiv — the same lookup that resolves a topic's seed papers.

The consequence is a real gap and it is reported rather than papered over: a pick linking to a blog post, a journal page or a project site has no bibliography to read, so it is skipped and named in the log. Measured over 25 issues of the shipped list, 237 of 250 picks carried an arXiv id and 13 did not. File one through inbox/ to archive it.

Which issues count as recent comes from the index's own order, matched to the page by the anchor each entry links to — not from assuming the page is sorted newest first. If no heading matches, the collector falls back to page order and warns: the quiet version of that failure reads the same issues forever while looking healthy.

Only the labelled link is followed (curated.link_label, default Paper). An issue's commentary often cites work the editor did not pick, and following those would archive what was mentioned rather than what was chosen.

  • A pick already in the archive is re-emitted, not looked up again. Deduplication joins sources with +, so the stored record becomes arxiv+curated and the fact that somebody chose it stops being invisible.
  • Picks are scored like anything else. A hand-filed PDF skips scoring because filing it is the group's own decision; a curated list is somebody else's, taken over a whole field. A general list mostly rejected against a narrow archive is the filter working.
  • A list that parses to zero papers warns. The format is one editor's markdown and can change without notice, and a silent zero looks exactly like a quiet week.

YouTube

pipelines/collect/youtube.py

GET https://www.youtube.com/feeds/videos.xml?channel_id=UCxxxxxxxxxxxxxxxxxxxxxx

Channel RSS, no API key. Videos shorter than youtube.min_duration_s (600 s in the shipped config) are skipped — shorts and teasers are not seminars. The feed carries no duration, so that filter only rejects videos whose duration is known from elsewhere.

Transcripts need the optional youtube-transcript-api package. Without it the ImportError is caught and videos are archived and flagged as transcript-less rather than failing.

PDF fetch

pipelines/collect/pdf_fetch.py

Not a discovery source. Once a paper has cleared scoring and is about to be queued for reading, its PDF is fetched so the reader gets the paper rather than a claim about it.

Why the document, not extracted text

Nothing here opens or parses the PDF. This repository's reader reads documents — figures, tables and all — and a result table settles what a paper achieved faster than the prose does. Running the file through a text extractor would discard exactly the part that carries the answer, in exchange for an external binary dependency.

Measured in a field archive: 38% of records built from abstracts had an empty results field, because the abstract carried no numbers.

A body served with HTTP 200 is checked for the %PDF- magic bytes — a paywall answers with a login page and a success status. Failure is ordinary: no pdf_url, an unreachable host or a paywalled venue leaves an abstract-only task, and roughly one paper in twelve has no obtainable PDF.

The inbox

pipelines/collect/local_pdf.py

The one collector whose source is a person, and the only one that touches no network. A PDF dropped into inbox/ is hashed, moved into data/pdfs/ under a content-addressed name, and recorded. The inbox drains on ingest — a move, not a copy, or the next run would ingest the same file again. Once the reading has been applied, render moves the document on to data/pdfs/read/, so what remains in data/pdfs/ is exactly the backlog.

  • Identity is the file's content, not its name. The same PDF filed twice under two names is one record.
  • A dropped PDF is never rejected by scoring. Filing it by hand is the editorial decision scoring exists to approximate.
  • Nothing reads it at ingest. The task asks whoever answers it to supply the bibliography from the document itself — the filename is not evidence.

04What happens to what comes back

Scoring

pipelines/enrich/score.py

Deliberately transparent: a keyword rule you can read and correct beats an opaque score you cannot argue with. A title hit is worth score.title_weight (3.0) and a body hit score.abstract_weight (1.0), because a term in the title is what the work is about while a term in an abstract may be a passing reference. A tracked author adds score.author_bonus. The raw sum is normalized as raw / (raw + title_weight), so one title hit lands at 0.5 and further hits add progressively less — which keeps thresholds comparable across topics with very different keyword-list sizes.

Matching uses word boundaries, so ATE does not match inside Water. The final word of a term also matches its regular English plural (action chunk → “action chunks”, robot policy → “robot policies”), because a keyword list one letter off produces “this topic has nothing to collect”, which is indistinguishable from a quiet week. Only the head word inflects, so latent action model matches “latent action models” but not “latent actions model”.

Items below a topic's threshold are still recorded in data/index/rejected.jsonl — the archive keeps a record of what was considered and rejected, so a threshold can be revisited without re-collecting.

Deduplication

pipelines/enrich/dedupe.py

Each paper is looked up under every identifier it could also be known by:

arxiv:2501.00001          ← version suffix stripped
doi:10.1000/example       ← lowercased
title:<fingerprint>       ← last resort

A match merges rather than replaces. A venue from a proceedings entry and an abstract from arXiv both matter, so fields are filled in: the stored record wins on identity, and the newcomer wins only where the stored record is empty or thinner. The alias map lives in SQLite at data/index/seen.sqlite and is committed, because a scheduled run starts from a fresh clone and would otherwise re-process everything.

05Knowing what was missed

pipelines/enrich/coverage.py

Every counter described so far reports what a collector found. None of them can distinguish “the source announced nothing today” from “we failed to read what the source announced today” — and those look identical in a log: a small number, no error.

arXiv heads each announcement day with its own entry count. That is the only number in this pipeline that the pipeline did not compute, which makes it the one thing that can tell the two apart. The sweep records three counts per category-day:

CountQuestionShort means
announcedWhat arXiv says the day held—
listedHow many identifiers we paginated throughWe stopped early. Costs more listing requests.
capturedHow many we hold an abstract forWe know exactly which to fetch. The cheap repair.

The two gaps are kept apart because they cost different amounts to close. A shortfall is recorded in data/index/coverage.jsonl as a debt, not an error: a bounded budget of it is paid each run, ordered by title relevance so the group gets what it wants soonest while the tail still drains. Counts only ever go up, so a run that paginated one page cannot erase the knowledge that an earlier run walked ten.

Abstracts land in data/abstracts/<category>/<day>.jsonl, separate from data/papers/. The first is what was published; the second is what the group tracks. Keeping them apart is what lets a threshold or a keyword list be revisited later against the real record rather than against whatever an old threshold happened to admit.

The ledger is committed; the abstracts are not

This repository gitignores data/abstracts/ and commits data/index/coverage.jsonl. The split is the point: at roughly 1.5 KB per paper the text would grow the repository by around 100 MB a year across four categories, while the audit of what is missing costs one line per category-day.

So a fresh clone starts with a large recorded debt and re-fetches against it, worst day first. That is the ledger working rather than failing — the one thing a clone must not lose is the knowledge of what it is missing. A deployment that would rather crawl less than carry the weight un-ignores the directory.

06Failure semantics

The governing rule: an unreachable source is logged and skipped, and that is not a failure of the run. A run completes with whatever the other sources returned, and the failure is recorded in the day's digest rather than being swallowed.

ConditionWhat happens
Connection error, timeout, truncated responseRetried up to collect.retries times with doubling backoff.
HTTP 429 / 408Retried like a transient error.
HTTP 4xx (other)Fails immediately, counts toward the circuit breaker.
Host fails N requests in a rowDropped for the rest of the process; further calls raise HostUnavailable with no network attempt.
One index of a multi-index collector failsLogged, recorded in errors, the others still run.
A collector raises unexpectedlyCaught at the run level; the other sources still run.
A scraped page parses to zero entriesLogged as a warning. A silent zero is the failure mode to fear.
PDF unreachable or paywalledAbstract-only reading task. Ordinary, not an error.
The failure this repository keeps guarding against

Not the loud one. The dangerous shape is a source that is alive, logs that are clean, and output that is a wrong subset looking like a complete one — a venue filter that quietly excluded every preprint, a keyword that missed its own plural, a parser that read a login link as a paper. Every warning above exists because one of those happened.

Turning a source off

Every source block has an enabled flag, and a run can be narrowed from the command line: 

python3 -m pipelines.run_daily --source local    # ingest inbox/ and nothing else
python3 -m pipelines.run_daily --topic <slug>    # one topic only
python3 -m pipelines.run_daily --days 30         # backfill a wider window
python3 -m pipelines.run_daily --dry-run         # what would be collected?

Generated from the collectors themselves. Where this document and pipelines/collect/ disagree, the code is right — and the disagreement is a bug in this page.
